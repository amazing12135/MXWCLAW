  问题 1：状态机顺序不合理 — COMPACT 在 COMMAND 之前

  分析：你说得对。/clear 只需清空 Session 即可，先做 Token 压缩是浪费。COMPACT 应该只在真正需要构建上下文之前触发。

  修改方案：

  调整状态顺序为：

  COMMAND → RESTORE → COMPACT → BUILD → RUN → SAVE → RESPOND → DONE

  逻辑：

  1. COMMAND 先执行 — 如果是 /clear / /stop 等命令，直接处理完返回，后续状态全部跳过
  2. RESTORE — 检查是否有未恢复的 Checkpoint，有则恢复
  3. COMPACT — 仅当 TokenBudget.usage_ratio() > 0.8（即当前 Session 消息占用超过 80% 预算时）才触发，否则直接跳过到 BUILD
  4. BUILD → RUN → SAVE → RESPOND → DONE — 正常流程

  关键改动：COMPACT 增加前置阈值判断，非每次必走。

  ---
  问题 2：每次消息都 Compact 开销大

  分析：Token 计数本身有成本，且绝大部分短对话不需要 compact。

  修改方案：

  在 Loop.run() 的 COMPACT 阶段增加守卫条件：

  # 伪代码
  if token_budget.usage_ratio(session) < 0.8:
      state.transition(BUILD)  # 跳过 COMPACT
  elif session.message_count > 20:
      # 仅在消息数超过阈值且 Token 压力大时才压缩
      session = episodic_memory.compact(session)
      state.transition(BUILD)

  两条硬规则：
  - Token 占比 < 80% → 跳过 compact
  - Token 占比 >= 80% 但消息数 < 20 → 也跳过（太短的对话压缩无意义，直接截断尾部即可）

  ---
  问题 3：Runner 每次迭代都保存 Checkpoint 开销过大

  分析：每次迭代写磁盘确实太重，尤其在工具调用快速返回的场景。

  修改方案：

  Checkpoint 保存改为策略驱动，仅在以下时机保存：

  ┌────────────────────────────┬─────────────────────────────────────────────────────────────────────────────┐
  │          保存时机          │                                    理由                                     │
  ├────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 工具调用执行前             │ 工具调用是最可能失败/超时的环节，在执行前保存可避免重试时重复消耗 LLM Token │
  ├────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ 每 N 次迭代（N=2，可配置） │ 纯文本多轮对话时的兜底保护                                                  │
  ├────────────────────────────┼─────────────────────────────────────────────────────────────────────────────┤
  │ Runner 异常退出时          │ except 块中紧急保存当前状态                                                 │
  └────────────────────────────┴─────────────────────────────────────────────────────────────────────────────┘

  # Runner 内部伪代码
  for i in range(max_iterations):
      response = await llm.chat(...)

      if response.tool_calls:
          # 工具调用前保存（最高风险点）
          await checkpoint.save(...)
          results = await execute_tools(response.tool_calls)

      elif i > 0 and i % checkpoint_interval == 0:
          # 每隔 N 次纯文本迭代保存
          await checkpoint.save(...)

      if response.finished:
          break

  正常完成时，工具调用前的 checkpoint 也不需要保留，prune() 清理即可。只有异常中断时才从 checkpoint 恢复。

  问题 4：记忆系统递归依赖风险

  分析：MemorySummarizer → 调用 LLM → LLM 触发 ContextBuilder.build_memory_context() → 又从 LongTermMemory 检索 → 反复注入记忆，形成循环。

  修改方案：

  方案 A（推荐）：内部 LLM 调用标记隔离

  在 LLMProvider.chat() 调用中增加 purpose 参数：

  class LLMCallPurpose(Enum):
      AGENT = "agent"        # 正常 Agent 对话，正常注入记忆
      SUMMARY = "summary"    # 摘要生成，不注入记忆
      SYSTEM = "system"      # 其他系统内部调用，不注入记忆

  ContextBuilder.build() 时检查 purpose：

  if purpose != LLMCallPurpose.AGENT:
      # 内部调用：最小上下文
      return [system_prompt_minimal] + messages  # 不注入 skills / memory

  MemorySummarizer 内部调用 LLM 时显式传入 purpose=SUMMARY，只用极简 system prompt，不触发任何记忆检索。

  方案 B：MemorySummarizer 使用独立的 ProviderRegistry 调用，直接用 LLM 原生 API，不走 ContextBuilder，彻底隔离。但这样会牺牲统一监控和管理。

  建议采用方案 A，在 AgentRunSpec 中增加 purpose 字段，保持统一接口。

  问题 5：流式输出到 Channel 的路径缺失

  分析：当前设计中 Hook 的 on_stream 只回调到 Loop 内部，没有路径把流式增量传给 Channel。用户在多轮工具调用的场景下会看到长时间无响应。

  修改方案：

  在 MessageBus 中增加流式通道：

  class MessageBus:
      # ... 现有字段 ...

      # 流式发布
      async def publish_stream_start(self, session_id: str, channel: str, chat_id: str) -> str:
          """返回 stream_id"""

      async def publish_stream_delta(self, stream_id: str, delta: str) -> None:
          """发送增量文本"""

      async def publish_stream_end(self, stream_id: str) -> None:
          """流结束"""

  BaseChannel 增加抽象方法：

  class BaseChannel:
      async def send_stream(self, chat_id: str, stream: AsyncIterator[str]) -> None:
          """流式发送，默认调用 send() 发完整消息"""

  Hook 的 on_stream 直接调用 bus.publish_stream_delta()。

  消息流变为：

  AgentRunner.run() → Hook.on_stream(delta)
    → Bus.publish_stream_delta(sid, delta)
      → Channel.send_stream()  # 微信/QQ/Email 各自实现流式输出

  OutboundMessage 增加字段区分完整消息和流式消息：

  class OutboundMessage:
      content: str
      is_streaming: bool = False      # 是否是流式消息的一部分
      stream_id: str | None = None    # 流式消息 ID

  问题 6：未考虑并发模型

  分析：多用户同时发消息时，单 Loop 串行处理会导致消息排队积压，用户体验差。

  修改方案：

  6.1 Session 级隔离并行

  class Loop:
      _session_locks: dict[str, asyncio.Lock]  # 每个 session 一把锁
      _active_runs: dict[str, asyncio.Task]    # 运行中的任务

      async def run(self, msg: InboundMessage) -> OutboundMessage:
          session_key = f"{msg.channel}:{msg.chat_id}"

          # 同一 session 串行（保证对话顺序）
          async with self._get_session_lock(session_key):
              return await self._process(msg)

          # 不同 session 并行（asyncio.gather 自然支持）

  模型：
  - 同一 (channel, chat_id) 的消息串行处理（一个用户的多条消息按序处理）
  - 不同 (channel, chat_id) 的消息并行处理（多个用户互不阻塞）

  6.2 MessageBus 改造

  class MessageBus:
      async def consume_loop(self):
          """Bus 消费循环：从 input_queue 取消息，按 session 分发"""
          while True:
              msg = await self.input_queue.get()
              session_key = f"{msg.channel}:{msg.chat_id}"
              asyncio.create_task(self._dispatch_to_loop(msg, session_key))

  6.3 全局并发上限

  class LoopPool:
      max_concurrent_sessions: int = 20  # 最多同时处理 20 个独立会话
      _semaphore: asyncio.Semaphore

  防止内存/CPU 过载。

  问题 7：缺乏消息去重机制

  分析：网络抖动或 Channel 重连可能导致同一消息重复投递。

  修改方案：

  7.1 InboundMessage 增加去重字段

  class InboundMessage:
      id: str          # 由 Channel 生成或从平台消息 ID 派生
      idempotency_key: str  # 去重键 = f"{channel}:{chat_id}:{platform_msg_id}"

  7.2 SessionManager 增加去重缓存

  class SessionManager:
      _recent_msg_ids: dict[str, set[str]]  # session_key → 最近 N 个消息 ID
      _dedup_window: int = 100              # 每个 session 保留最近 100 个 ID

      def is_duplicate(self, msg: InboundMessage) -> bool:
          key = msg.idempotency_key
          session_key = f"{msg.channel}:{msg.chat_id}"
          if key in self._recent_msg_ids.get(session_key, set()):
              return True
          self._recent_msg_ids[session_key].add(key)
          # LRU 淘汰（超过 100 个时移除最早的）
          return False

  7.3 去重在 Loop 入口处统一执行

  # Loop.run() 开头
  if self.session_mgr.is_duplicate(msg):
      log.warning(f"Duplicate message dropped: {msg.idempotency_key}")
      return None  # 丢弃重复消息

  问题 9：SubAgent 缺乏关键定义

  分析：当前 SubAgent 定义过于简单，缺少错误处理、资源限制、结果格式、隔离模型等。

  修改方案：

  9.1 SubAgent 完整定义

  @dataclass
  class SubAgentConfig:
      task: str                     # 任务描述
      model: str | None = None      # 模型（None=继承父Agent）
      max_iterations: int = 5       # 最大迭代次数
      timeout_seconds: int = 120    # 总超时（子代理任务通常较长）
      restrict_to_workspace: bool = True
      inherit_memory: bool = False  # 是否继承父Agent的工作记忆
      allowed_tools: list[str] | None = None  # None=全部, [] = 空列表

  @dataclass
  class SubAgentResult:
      agent_id: str
      status: SubAgentStatus
      content: str | None           # 最终输出
      iterations: int
      token_usage: TokenUsage
      tool_calls_made: int
      error: str | None
      duration_seconds: float
      events: list[SubAgentEvent]   # 关键事件日志

  @dataclass
  class SubAgentEvent:
      timestamp: datetime
      event_type: str  # "spawned" / "tool_call" / "iteration" / "error" / "done"
      detail: str

  9.2 SubAgentManager 完善

  class SubAgentManager:
      max_concurrent: int = 5
      _active: dict[str, SubAgent]
      _semaphore: asyncio.Semaphore
      _results: dict[str, SubAgentResult]  # 保留最近结果供查询

      async def spawn(self, config: SubAgentConfig) -> str:
          """启动子代理，返回 agent_id"""
          async with self._semaphore:
              agent = SubAgent(id=uuid4(), config=config)
              self._active[agent.id] = agent
              asyncio.create_task(self._run_and_cleanup(agent))
              return agent.id

      async def cancel(self, agent_id: str) -> None:
          """取消子代理"""
          agent = self._active.get(agent_id)
          if agent:
              agent._cancel_event.set()

      async def status(self, agent_id: str) -> SubAgentResult | None

      async def wait(self, agent_id: str, timeout: float | None = None) -> SubAgentResult

  9.3 隔离模型

  SubAgent 隔离清单:
  ├── 独立 ToolRegistry（不含 spawn_tool，防递归）
  ├── 独立 Session（不共享父 Session，不写入 JSONL）
  ├── 独立 FileStates（写缓存隔离）
  ├── 独立 ContextBuilder（精简系统提示词，不注入 Skills）
  ├── 可选择是否继承父 Agent 的 WorkingMemory
  ├── 工作目录 = workspace / subagents / {agent_id}
  └── 超时后强制取消（asyncio.wait_for + cancel scope）

  9.4 错误处理

  try:
      result = await asyncio.wait_for(
          self.runner.run(spec),
          timeout=config.timeout_seconds,
      )
  except asyncio.TimeoutError:
      result = SubAgentResult(status=CANCELLED, error="Timeout")
  except Exception as e:
      result = SubAgentResult(status=ERROR, error=str(e))
